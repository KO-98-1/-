# 입력 자료에서 사실 추출하기

회의록은 형식이 제각각이다. 조사한 공개 회의록(공공 SI 회의록 양식, GitHub 공개 프로젝트 회의록 등)은 대체로
다음 블록으로 이루어진다. 블록마다 산출물로 가는 길이 다르다.

| 회의록 블록 | 흔한 표기 | 주로 가는 곳 |
|---|---|---|
| 회의 개요 | 일시·장소·참석자·주관·회의명 | 입력 색인(날짜), 이해관계자(R2), 조직(D6 4.6) |
| 안건 / 아젠다 | 안건, Agenda, 논의 주제 | 서브시스템 배분의 단서 |
| 논의 내용 | 논의사항, 회의 내용, 주요 내용 | 요구사항 설명, 시나리오, 제약사항 |
| **결정 사항** | 결정사항, 합의사항, 결론, Decision | 요구사항(확정), 해결방안, 아키텍처 결정 → `fact` |
| **미결 / 추후 검토** | 미결 항목, 이슈, 추후 결정, 검토 필요, Open issue, TBD | `_meta.tbd` (미정) |
| 조치 사항 / Action Item | 조치사항, To-do, 담당·기한 | 일정(D6 4.7) 참고 — 요구사항 아님 |
| 향후 일정 | 차기 회의, 일정 | 사업관리용 → 산출물 대상 아님(가이드 범위 제외) |

## 추출 절차 (마스터)

1. `swd ingest` 후 `.work/inputs/index.yaml`과 각 `.txt`를 읽는다(원본 파일 대신 정규화 텍스트를 읽는다: 줄 번호 고정·개인정보 마스킹).
2. 시스템 전체 그림을 잡는다: 시스템명, 사용자 유형(액터 후보), 업무 영역(서브시스템 후보), 외부 연계, 비기능 요구(성능·보안·가용성).
3. **서브시스템 배분표**(`.work/allocation.yaml`)를 만든다: 서브시스템별로 관련 입력ID와 줄 범위, 핵심 요지.
   여러 서브시스템에 걸친 비기능 요구·공통 기능(로그인, 권한, 공통코드)은 `COM`(공통)으로 보낸다.
4. 입력 간 **충돌**(같은 기능에 대한 다른 결정, 날짜가 다른 회의록의 번복)은 최신 날짜를 우선하되, 충돌 사실을 게이트에서 보고한다.

## 문장 → 요구사항 판단 기준

- "~해야 한다 / ~하기로 함 / ~기능 필요 / ~할 수 있어야" → 요구사항 후보. 결정 사항 블록에 있으면 확정(`fact`).
- 아이디어 메모의 "~하면 좋겠다 / 검토" → 요구사항 후보이되 중요도 등은 비움, 필요시 `tbd`.
- 한 문장에 여러 기능이 있으면 **업무 단위로서 가치를 가지는 단위**로 나눈다(가이드 R1 작성 목적).
- 성능·보안·품질 수치는 원문 그대로 옮긴다(단위 포함). 수치가 없으면 검수기준은 비운다.
- 요구사항이 아닌 것: 회의 진행, 산출물 작성 일정, 인력 배치 → 제외(가이드: 사업관리용 산출물은 대상 제외).

## 수정사항(CR) 처리

수정사항 입력은 새 요구가 아니라 **기존 항목의 변경**일 수 있다.
1. 영향을 받는 ID를 찾는다(요구사항 → 유스케이스 → 화면·클래스·테이블·시험까지 추적표 방향으로).
2. 충돌 판정: 승인된(confirmed 또는 fact) 항목의 값을 바꾸는 변경, 회의 결정과 반대되는 변경 → **충돌**.
3. 변경안(무엇을·어떻게)과 충돌 목록을 사용자에게 보여주고 **확인을 받은 뒤** 반영한다.
4. 반영 시 해당 항목의 `_meta.sources`에 CR 입력ID를 추가하고, `swd history add`로 영향받은 산출물마다 이력을 남긴다.
