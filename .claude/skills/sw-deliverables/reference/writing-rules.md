# 산출물 작성 원칙 (모든 작성자·서브에이전트 공통)

근거: CBD SW개발 표준 산출물 관리 가이드(2011.12) — 산출물 양식 → 작성 목적 → 작성 방법 → 항목 설명 → 작성 사례.
문서는 프로그램이 양식대로 찍어내므로, 작성자는 **model/<서브시스템>/<코드>.yaml 데이터만** 채운다.

## 1. 값의 세 가지 출처 — `_meta.origin`

| origin | 언제 | 필수 기록 | 문서 표시 |
|---|---|---|---|
| `fact` | 입력 자료(회의록·아이디어·수정사항·참고문서)에 근거가 있다 | `sources: [MTG-001:12-18]` (입력ID:시작줄-끝줄) | 일반 |
| `ai` | 입력에 직접 없지만 가이드 작성 방법상 **분석 산출물로부터 논리적으로 도출되는 설계**(클래스·컴포넌트·테이블·시험케이스·시나리오 등) | `sources`가 있으면 근거가 된 입력/산출물 | 노란 음영(검토 전) |
| `derived` | 다른 산출물에서 기계적으로 옮긴 것(추적 ID, 복사) | 선택 | 일반 |

- `fact` 항목 안에서 일부 필드만 추정했다면 `ai_fields: [priority, acceptance]` 처럼 **필드명**을 적는다. 그 칸만 음영 처리된다.
- 줄 번호는 `.work/inputs/<ID>.txt` 를 Read 도구로 읽었을 때 보이는 번호다. 여러 곳이면 모두 적는다.

## 2. 비워 두는 규칙 — 추측 금지

정보가 없으면 **키를 생략**한다. 렌더러가 `(정보 부족)`으로 표시한다.
해당 항목이 **없는 것이 확실한** 목록(예: 속성이 없는 컨트롤 클래스, 대안 흐름이 없는 유스케이스)은 빈 목록 `[]`으로 명시한다 → `해당 없음`.
`(정보 부족)`, `(미정)`, `해당 없음`, `TBD`, `-` 같은 표시 문자열을 **값으로 쓰지 않는다.**

다음은 입력 자료에 없으면 AI 제안으로도 채우지 않는다(사실만 가능):
- 사람·부서·담당자 이름, 승인자, 외부기관·외부 시스템의 실제 명칭과 담당자
- 수치 목표(응답시간, 동시사용자, 건수, 용량, 가용률), 일정·기간·비용
- 법령·규정·표준의 명칭, 보안 등급, 계약 조건
- 서버 사양·IP·제품명(DBMS·WAS 제품 등), 실제 시험 결과

반대로 다음은 가이드가 요구하는 **설계 행위**이므로 `origin: ai`로 작성해도 된다:
- 유스케이스의 기본/대안 시나리오 세부 단계(회의록의 기능 설명에서 전개), 전제·종료조건
- 시퀀스 메시지, 설계 클래스·속성·오퍼레이션, 컴포넌트 그룹핑, 인터페이스 오퍼레이션
- 엔티티·속성·관계, 테이블·컬럼(타입은 일반적 관례), 화면 입출력 항목, 시험 시나리오·케이스
- 요구사항 구분·중요도 같은 분류 판단(근거 문장이 있으면 `fact` + 해당 필드만 `ai_fields`)

## 3. 미정 — `_meta.tbd`

입력 자료에 "추후 결정", "검토 필요", "미결", "TBD", "다음 회의에서" 등으로 **논의됐지만 결정되지 않은** 사항은
해당 필드를 비우고 `tbd: {필드명: "사유(원문 요약)"}` 로 기록한다. 문서에는 `(미정)`으로 표시된다.

## 4. 문체와 형식

- 가이드 작성 사례처럼 "~한다" 체의 간결·구체적 문장. 모호한 표현(적절히, 등등) 대신 대상·조건·결과를 쓴다.
- 여러 줄 항목(시나리오, 전제조건, 처리 내용 등)은 YAML 목록으로 쓴다. 번호·글머리는 렌더러가 붙인다.
- 대안 시나리오는 `[{name: "가. 취소 신청", steps: ["…", "…"]}]` 형식.
- `요구사항 출처`는 비워 두면 `_meta.sources`의 입력 문서 번호·제목·일자로 자동 기재된다(RFP 등 다른 문서번호가 있으면 직접 쓴다).
- 설계단계 산출물(D7·D10·D11)과 인수시험 시나리오(T6)의 `result`(시험결과)는 쓰지 않는다(가이드: 설계단계에서는 기술하지 않음).
- 버전 칸은 쓰지 않는다(설정: fill_version=false).

## 5. ID

- `sw-config.yaml` 의 `ids.element` 규칙을 따른다. 프롬프트에 서브시스템별 **다음 번호**가 주어진다.
- 한 번 부여한 ID는 바꾸거나 재사용하지 않는다. 삭제된 항목의 번호는 비워 둔다.
- 요구사항 ID의 분류코드는 구분과 일치해야 한다(기능=SFR, 성능=PER, 품질=QUR, 인터페이스=SIR, 데이터=DAR, 운영=OPR, 제약=COR, 보안=SER, 테스트=TER …).
- 하위 ID(시험 케이스 등)는 상위 ID 뒤에 `-01, -02`를 붙인다(예: IT-SA-001-01).
- 다른 서브시스템의 항목은 **ID로만 참조**하고 그 파일은 수정하지 않는다.

## 6. 다이어그램

유스케이스도·시퀀스도·클래스도·ERD·메뉴 구조도·컴포넌트 구조도·화면 와이어프레임은 **데이터에서 자동 생성**된다.
Mermaid 코드를 직접 쓰지 말고 데이터(액터·유스케이스 관계, 메시지, 관계, 메뉴 경로, 의존관계, 입출력 항목)를 정확히 채운다.
아키텍처·구성도처럼 데이터 스키마가 없는 그림만 `mermaid` 필드에 직접 쓴다 → `reference/diagram-style.md` 준수.

## 7. 가이드 불일치 처리(상황에 맞게)

- 명칭: 산출물 목록(Ⅱ.1) 명칭을 쓴다. 양식 제목이 다른 경우(D4 '인터페이스 정의서')는 양식 제목을 표지에 쓴다.
- 요구사항 추적표(R3)는 AI가 쓰지 않는다 — 각 산출물의 ID 연결(usecase_id, requirement_ids 등)을 정확히 채우면 자동 생성된다.
- 화면 속성 표기: 항목 설명의 `RO`(ReadOnly)를 쓴다(사례의 `R`은 쓰지 않음).
- 개념적 클래스 모형 기술서는 코드 R5, 용어집은 R4로 표기한다(가이드 사례의 R3 중복 회피).
- 가이드 양식 항목이 프로젝트에 맞지 않으면 억지로 채우지 말고 비워 둔다(정보 부족) — 양식 자체는 바꾸지 않는다.
